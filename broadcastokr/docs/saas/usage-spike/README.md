# Usage-metrics spike — 2026-10-01

Follow-up to `../2026-09-04-usage-telemetry-idea.md`. Question: can the cockpit
measure how each client uses WHATS'ON with SELECT-only, one-number queries?
**Answer on structure: yes.** Real data is still untested (see Open questions).

## What the schema offers

Found via `../../../../whats-on-semantic-query-workbench` (full PSI dictionary snapshot):

- `PSI.T3TMETRIC`: one row per save (commit), with user name, session, service or person,
  timestamps pre-bucketed by day/hour/minute, insert/update/delete counts and durations.
  `PSI.T3TTABLEMETRIC` lists the tables each save touched, which identifies the module.
- `PSI.PSIUSER`: enabled/disabled, server user, `USR_LASTLOGONTIME`.
- Status logs (`PSIPRDSTATLOG`, `CM2CONTRACTSTATUSLOG`, `WONDAYSTATUSLOGENTRY`, and 10 more)
  for workflow throughput.
- `PSI.MGXINSTALLATIONHISTORY` (upgrades) and `PSILOGGING.WONCRASHREPORTLOG` (crashes).
- `AMUSERACTION`, `MGXPERFORMANCETRACELOG`: per-command usage, empty on every rig seen
  (probably opt-in).

## The lab

- `wonpoc` (Postgres 17, :5433) has the real structure but no usage rows.
- `brokr_usage_lab` (same server) holds the 10 usage tables copied structure-only from
  `wonpoc` (FKs dropped), once per fictional client. The three clients are schema pairs
  `a_psi`/`a_psilogging` etc.:
  - **a** = steady and broad use;
  - **b** = declining use;
  - **c** = single module.
- All data is invented (`generate_lab_data.py`, seeded, 180 days up to 2026-10-01).

Rebuild:

1. `pg_dump -s` the ten tables from `wonpoc` into `wonpoc_usage_ddl.sql`.
2. Run `build_lab_schema.py`, then `generate_lab_data.py`, then `run_metrics.py`.

## Result

`metrics.py` holds 17 candidate metrics in 5 groups, each with a PostgreSQL and an Oracle text:

- Adoptie (adoption)
- Intensiteit (intensity)
- Breedte (breadth)
- Werkprocessen (workflows)
- Platform

Every text passes the bridge's `assertReadOnlySelect`. The PostgreSQL texts ran read-only
on all three lab clients and on `wonpoc`: they return one `value` each, in under 1.5 s.
The three profiles separate clearly:

- client b's active users trend is −36 %;
- client b's seat utilisation is 32 % against 95 % for a;
- client b has 63 crashes against 6 for a;
- client b's last upgrade was 415 days ago.

`results.json` has the full numbers.

**The Oracle texts have not been run**: the local Oracle no longer holds a WHATS'ON schema.

## Checking a real client (remote)

Client databases are too large to load locally (up to 150 GB), so the check runs where
the database is. `remote_check_oracle.sql` is generated by `build_remote_script.py` from
`metrics.py`. It is read-only and has 7 statements:

- 5 profile statements: is usage logged and since when, people vs services, application
  ids, tables touched, duration magnitude;
- the PSI metrics;
- the PSILOGGING metric.

It returns counts and metric values only: no user names, no business rows. Every statement
passes `assertReadOnlySelect`. It has not yet been run on Oracle.

## Findings for the build

- `bridge/whatson/core.cjs:285` turns a NULL result into `0` (`Number(null)`). For usage
  metrics, "no data / logging off" must stay distinguishable from a real 0.
- A high automation share can mean the people stopped using WHATS'ON while services run
  on (client b: 91 %). Read it together with active users, never alone.
